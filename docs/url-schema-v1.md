# URL Schema V1

## Table Purpose

The first database table should store the core shortened URL mapping.
Each row should represent one shortened URL created by the service.
The table only needs to support create and resolve behavior for now.

## Columns

### `id`

This is the internal row identity.
It should be the primary key and be generated by the database.
It is useful even if `short_code` is also unique.

### `short_code`

This is the public code used in redirect lookups.
It must be unique because two rows cannot represent the same short code.
This column should also support fast lookup.

### `original_url`

This stores the full destination URL.
It should be required because a short code without a destination is invalid.

### `created_at`

This stores when the short URL was created.
It is useful for debugging, future analytics, expiry logic, and operational visibility.

### `updated_at`

This stores when the short URL row was last modified.
It is useful for future schema evolution, admin operations, expiry updates, and general data hygiene.
On initial insert, it should start with the same value as `created_at`.

## Why We Need `id`

`short_code` is a business identifier, but `id` is a stable internal database identifier.
Keeping them separate makes the schema easier to evolve later.
It is also a very common production pattern.

## Why `short_code` Must Be Unique

The redirect path depends on one short code mapping to exactly one destination URL.
If duplicate short codes existed, redirect behavior would be ambiguous and incorrect.
The database should enforce this rule, not only the application code.

## What We Are Not Adding Yet

We are not adding `redirect_count`, `deleted_at`, or user-related fields yet.
`expires_at` is now part of the evolving model design, but it is not fully enforced in application behavior yet.
The schema is still being kept intentionally small while becoming more production-oriented.
